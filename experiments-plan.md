# Experiments plan — Kedro pipeline

**Status: designed, not built.** This is a decision record so the pipeline can be built without
redoing the design work. Nothing here has been run, so treat the numbers as arithmetic and the
prompt design as a hypothesis.

## What the experiment is for

The app hard-codes one model as judge. This pipeline exists to answer whether that was the right
pick, along two axes:

1. **Which free model is the most consistent judge?** Consistency, not generosity — a judge that
   scores the same answer 40 one run and 80 the next is useless regardless of its average.
2. **Does an explicit rubric in the judge prompt reduce that variance?**

## Comparison set

Only four models on OpenRouter's free tier support strict structured output, and structured output
is non-negotiable here (see below). That makes the comparison set self-selecting:

| Model | Context |
|---|---|
| `openai/gpt-oss-20b:free` | 131k |
| `google/gemma-4-26b-a4b-it:free` | 262k |
| `nvidia/nemotron-nano-9b-v2:free` | 128k |
| `nvidia/nemotron-3-super-120b-a12b:free` | 262k |

Two of the four are NVIDIA variants, so a four-way comparison is really three vendors with one size
axis inside NVIDIA. Worth remembering when reading the report.

## Pipeline

Four nodes, run in sequence:

| # | Node | In | Out |
|---|---|---|---|
| 1 | `generate_questions` | topic, difficulty, num_questions, prompt_version | question list |
| 2 | `generate_sample_answer` | each question | a plausible candidate answer |
| 3 | `score_answer` | question + answer, judge model, prompt_version | 3 scores + feedback, or a recorded failure |
| 4 | `compare_report` | all scores | comparison table: mean, variance, response time, parse failures per combo |

Node 2 exists so scoring can be exercised without a human typing an answer every run.

## Decisions

### Sweep the judge, fix everything upstream

Nodes 1 and 2 run on **one fixed model**. Only node 3's model varies.

If every model generated its own questions, answered them, and graded them, a high score would be
unattributable — easier questions, better answers, or a softer judge, with no way to tell which.
Fixing the upstream means each judge grades **the same answers**, so the only thing moving is the
thing being measured.

Cost: the fixed generator's quirks are baked into every comparison. Accepted — the question is
"which judge is consistent", not "which model is best overall".

### Prompt versions

Both prompt families are versioned, but only the judge's versions are interesting:

- **v1** — plain persona. "You are a strict but fair interviewer. Score 0–100 on…"
- **v2** — v1 plus an explicit rubric with per-band definitions ("90–100: correct and complete,
  addresses edge cases the question implies; 70–89: correct with gaps; …").

The measurable claim: **v2 produces lower score variance than v1 on identical input.** If it
doesn't, the rubric is decoration and the app should keep the shorter prompt.

Question-generation versions differ on terse vs. detailed instructions. Lower priority — question
quality needs a human to judge, which this pipeline cannot do.

### Structured output is forced, and failures are results

Every call sends `response_format` with a strict JSON schema. When a response still fails to parse:

- Retry **once**.
- If it fails again, **record it as a parse failure** for that (model, prompt_version) combo and
  move on. The run continues.

This deliberately differs from the app, which never retries. The app has a human waiting and a
budget to protect, so it surfaces the error and lets them decide. The pipeline is measuring failure
rates unattended, so it needs the run to survive a single bad response — but it must count it.

Never regex-scrape a mangled response into a score. Doing so converts "this model cannot hold a
schema" into "this model scored 72", which deletes the exact signal the experiment exists to
produce. Parse failure rate is a column in the report, not an error to be swallowed.

Note that strict schemas guarantee *shape*, not *range* — providers routinely ignore
`minimum`/`maximum`. A score of 340 is schema-valid. Range-check in the node, and count a
range violation as a failure. (`app/lib/score.ts` does this for the app; the pipeline needs its own
copy — the two codebases are deliberately independent.)

### The sweep is a loop inside one node

Kedro's DAG is static, so a model × prompt grid has to be either a namespaced modular pipeline
generated by a Python factory at build time, or an ordinary `for` loop inside a single node.

**Use the loop.** The catalog, dataset versioning and `--params` all work either way. The factory
buys a prettier `kedro viz` and costs a pipeline-generation layer to debug when a run misbehaves.

## Request budget — read this before running anything

OpenRouter free tier, no credits purchased: **20 requests/minute, 50 requests/day**. The daily cap
rises to 1000 only once $10 of credits has been purchased at some point.

A full grid does not fit:

| Node | Calls | Working |
|---|---|---|
| `generate_questions` | 8 | 4 models × 2 prompt versions |
| `generate_sample_answer` | 24 | 8 combos × 3 questions |
| `score_answer` | 24 | one per answer |
| **Total** | **56** | **exceeds the 50/day cap** |

So the shipped default must be smaller. With the judge-only sweep, generation happens **once** and
is reused across every judge:

| Node | Calls | Working |
|---|---|---|
| `generate_questions` | 1 | fixed model, one prompt version |
| `generate_sample_answer` | 3 | fixed model, 3 questions |
| `score_answer` | 12 | 2 judges × 2 prompt versions × 3 questions |
| **Total** | **16** | leaves ~34/day for the app |

Widening to all four judges with both prompt versions costs 4 × 2 × 3 = 24 scoring calls, so 28
total. That still fits, and it is the widest grid that does — because generation is not swept, the
judge count multiplies only the 3-call answer set, not the whole pipeline. Sweeping generation as
well is what pushes past 50 (the 56-call table above).

Two consequences the implementation must respect:

- **Cache LLM responses on disk**, keyed on `(model, prompt_version, input_hash)`. A re-run of a
  combo already seen must cost zero requests. Without this, one crashed run burns the day.
- **Reuse generated questions and answers across judges within a run.** Regenerating them per judge
  both wastes requests and breaks the "same answers for every judge" property that makes the
  comparison valid.

## `parameters.yml` sketch

```yaml
topic: "system design"
difficulty: "mid-to-senior"
num_questions: 3

# Fixed for question and answer generation — not swept.
generator_model: "openai/gpt-oss-20b:free"
generator_prompt_version: "v1"

# Swept. Every judge scores the same generated answers.
judge_models:
  - "openai/gpt-oss-20b:free"
  - "google/gemma-4-26b-a4b-it:free"
judge_prompt_versions: ["v1", "v2"]

max_retries: 1
cache_dir: "data/08_cache"
```

Overridable per run without touching code:

```bash
kedro run --params topic="system design",judge_models=["google/gemma-4-26b-a4b-it:free"]
```

## Catalog sketch

Every LLM output is versioned so runs can be compared over time.

```yaml
questions:
  type: json.JSONDataset
  filepath: data/02_intermediate/questions.json
  versioned: true

sample_answers:
  type: json.JSONDataset
  filepath: data/02_intermediate/sample_answers.json
  versioned: true

scores:
  type: json.JSONDataset
  filepath: data/03_primary/scores.json
  versioned: true

comparison_report:
  type: pandas.CSVDataset
  filepath: data/08_reporting/comparison.csv
  versioned: true
```

`scores` holds one record per (judge_model, prompt_version, question) with the three scores,
feedback, elapsed milliseconds, and a `parse_failed` flag — everything `compare_report` needs to
aggregate without a second pass over raw responses.

## Report columns

One row per (judge_model, prompt_version):

`mean_correctness`, `mean_english`, `mean_depth`, `stdev` per criterion, `mean_latency_ms`,
`parse_failures`, `n`.

**The stdev columns are the answer.** Means tell you a model is generous; standard deviation across
identical inputs tells you whether you can trust any single score it produces. A judge with a
flattering mean and a wide spread is worse than a harsh consistent one.

## Open questions

- **Variance across identical inputs needs repeats.** As specified, each judge scores each answer
  once, which gives variance *across questions*, not *across runs of the same question* — a
  different quantity. Measuring judge consistency properly needs the same (question, answer) scored
  N times per judge, which multiplies the request count by N. At 50/day this is the constraint that
  will actually bite. Decide N before building.
- Nothing checks question *quality*. The pipeline can compare judges but cannot tell you whether
  the generated questions were any good — that needs a human.
- `topic` and `difficulty` are experiment-side knobs with no app equivalent. The app generates from
  role alone. If the experiment concludes something about topic phrasing, the app cannot act on it
  without new UI.
